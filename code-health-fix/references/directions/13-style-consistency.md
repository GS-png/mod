# 13. 代码风格与一致性

## 这个方向要解决什么

找“同一块代码地盘里，写法像三个不同人吵架留下的痕迹”的问题。
风格一致性像路边的指示牌，同一条路上牌子方向和叫法都不一样，人就会越走越懵。

## 什么时候把它列为不同评级

- `必须`：当前不一致已经影响理解、导致误用，或者用户明确要求统一风格
- `建议`：同目录相邻文件风格混乱，读起来成本明显偏高
- `可选`：只有少量轻微不一致，不影响理解
- `不必`：当前主目标是 bug 修复或结构治理，风格并不构成阻碍

## 检查边界

- 只统一最影响理解的局部风格
- 不做大面积格式化表演
- 同时看生产代码和相关测试，避免一边统一一边更乱

## 先收集这些证据

- 同目录相邻文件、公共 helper、返回模型
- 空值处理、命名、布尔语义、异常返回习惯
- 测试命名和断言风格
- 团队现有 lint、editorconfig、格式化规则

## 分步检查

1. 找出当前范围里最刺眼、最影响理解的不一致点
2. 判断这些不一致是否真的会导致误读或误用
3. 选一个最小统一规则，不要发明新流派
4. 只改当前边界内受益最大的几处
5. 看测试和文档里的命名是否也要同步

## 修复要求

- 优先统一命名、返回语义、空值处理、测试命名这些会影响理解的点
- 尊重仓库现有主风格，不强推个人喜好
- 必要时借助现有 lint 或格式化规则验证

## 完成标志

- 当前边界里最影响理解的不一致点已经收口
- 调用方和测试的语义更统一
- 没引发大面积无价值 diff

## 不要做

- 不要借机全仓格式化
- 不要因为个人偏好改掉团队既有稳定风格
- 不要把真正的逻辑问题伪装成“只是风格问题”
