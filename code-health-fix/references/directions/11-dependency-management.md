# 11. 依赖管理

## 这个方向要解决什么

找“项目背着哪些不该背的包袱”的问题。
依赖像家里请来的工具人，请多了会挤满客厅，请错了还会带来额外风险和维护成本。

## 什么时候把它列为不同评级

- `必须`：用户明确要求查依赖，或者已经看到未使用依赖、重复依赖、锁文件漂移、过重依赖
- `建议`：当前改动会触碰构建、打包、运行时装载链
- `可选`：主问题与依赖无关，但顺手有明显清理机会
- `不必`：本轮完全是局部代码修复，依赖层没有任何信号

## 检查边界

- 以“保留、删除、替换”的证据为核心
- 默认不做升级大动作，除非用户明确授权
- 同时看依赖清单、锁文件、构建脚本，不只看一个地方

## 先收集这些证据

- 包管理文件、锁文件、构建脚本
- 实际 import/using/引用位置
- 运行时装载、插件机制、DLL 依赖
- 相关 CI、发布脚本

## 分步检查

1. 列出当前范围直接使用的依赖
2. 看有没有声明了但没用的依赖
3. 看有没有同类依赖重复存在，职责重叠
4. 看版本范围是否过宽，锁文件是否漂移
5. 看大依赖是不是只用了很小一块能力
6. 看删除或替换后会不会影响构建和运行

## 修复要求

- 优先删未使用依赖和明显重复依赖
- 如果只是发现升级机会，先记账，不默认执行
- 变更后至少做构建或最小运行验证

## 完成标志

- 能说明每个改动依赖为什么保留、删除或暂缓
- 锁文件和依赖声明保持一致
- 没因为清理依赖把构建链打断

## 不要做

- 不要把“版本旧”直接等同于“必须升级”
- 不要只改依赖清单，不管锁文件和构建脚本
- 不要删除看起来没用、但实际通过反射或动态装载使用的依赖
