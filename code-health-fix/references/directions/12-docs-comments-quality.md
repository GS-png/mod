# 12. 文档与注释质量

## 这个方向要解决什么

找“代码已经变了，但说明书还停在旧版本”的问题。
文档和注释像路标，路都改道了，牌子不改，后面的人一定会走错。

## 什么时候把它列为不同评级

- `必须`：本轮会改公共接口、配置、复杂逻辑，或现有注释已经与行为不一致
- `建议`：模块复杂，靠上下文才能理解，但注释和文档不足
- `可选`：当前改动很小，且不影响外部使用方式
- `不必`：纯内部小修，且没有注释失真问题

## 检查边界

- 重点更新本轮触达的文档、注释、配置说明
- 不默认发起全仓文档翻新
- 注释要解释“为什么”和“关键约束”，不是把代码翻译一遍

## 先收集这些证据

- README、模块说明、配置说明
- 公共接口注释、复杂逻辑注释
- 最近改动代码附近的注释
- 用户实际使用入口和参数说明

## 分步检查

1. 看注释和代码行为是否一致
2. 看公共接口是否说明了输入、输出、约束和副作用
3. 看复杂分支有没有必要背景，帮助后来人理解
4. 看配置项是否说明含义、默认值和可选值
5. 看 README 或模块文档是否还指向旧路径、旧命令、旧行为

## 修复要求

- 只更新本轮真正触达且会误导人的部分
- 注释优先解释意图、边界、风险，不写废话
- 文档修改后要和代码当前行为一致

## 完成标志

- 本轮触达的说明和代码一致
- 公共入口的关键用法能直接看懂
- 复杂逻辑旁边有足够但不过量的解释

## 不要做

- 不要写“处理数据”“执行逻辑”这种空注释
- 不要把代码逐行翻译成中文注释
- 不要只改代码，不同步更新明显过时的文档
