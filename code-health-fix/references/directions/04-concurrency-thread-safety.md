# 4. 并发与线程安全

## 这个方向要解决什么

找“一个人跑没事，多个人一起跑就乱套”的问题。
并发 bug 像多人同时抢同一个抽屉里的钥匙，单看每个人动作都对，合在一起就会打架。

## 什么时候把它列为不同评级

- `必须`：存在共享可变状态、缓存、事件回调、异步任务、锁、取消 token、后台线程
- `建议`：模块是异步的、可能重入，但共享状态不多
- `可选`：纯同步且无共享状态的小模块
- `不必`：纯静态资源、说明文档、离线常量文件

## 检查边界

- 重点查共享状态和时序，不把纯性能问题混进来
- 同时看创建方、读写方、销毁方，不只看其中一侧
- 如果仓库没有并发使用场景证据，不要强行凑并发问题

## 先收集这些证据

- `async/await`、任务调度、计时器、事件回调
- 全局状态、单例、缓存、静态集合
- `lock`、`Semaphore`、`Monitor`、取消 token
- 相关测试和复现脚本

## 分步检查

1. 画出共享状态是谁在写、谁在读
2. 看异步链里是否存在未等待、重复进入、回调重入
3. 看锁范围是否过大、过小，顺序是否可能互相卡住
4. 看取消是否真的传下去，还是只在外面摆样子
5. 看读改写操作是否具备原子性
6. 看对象释放或状态清理时，其他线程会不会还在使用

## 修复要求

- 先收窄竞态窗口，再考虑是否需要加锁
- 能用更简单的不可变数据、局部变量，就别堆复杂同步原语
- 并发修复后，最好补最小复现或重复运行验证

## 完成标志

- 能说明竞态窗口在哪里、怎么被关闭
- 共享状态的读写边界清楚
- 修复后不会引入新的死锁或假取消

## 不要做

- 不要看到 `async` 就自动判成并发问题
- 不要只加一把大锁就宣称解决，先确认不会锁死主路径
- 不要忽略取消、释放、回调这些容易漏的边角
