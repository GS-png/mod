# 9. 重复代码清理

## 这个方向要解决什么

找“同一件事在多个地方抄了很多遍”的问题。
重复代码像厨房里放了三份调料配方，只要有一份忘了改，味道就会开始跑偏。

## 什么时候把它列为不同评级

- `必须`：用户明确要求“减少重复”，或者已经看到同一规则在多处分叉
- `建议`：有多处相似实现，已经影响维护成本
- `可选`：只有轻微相似，还没形成真正维护负担
- `不必`：当前范围内没有重复块，或只是偶然相似的简单代码

## 检查边界

- 只处理语义相同或强相关的重复，不为抽象而抽象
- 优先清理当前边界内最痛的一组重复块
- 抽取后要保证调用点语义仍然清楚

## 先收集这些证据

- 相似命名的方法、类、辅助函数
- 多个入口里的相同校验、转换、组装逻辑
- 不同模块里复制粘贴的历史实现
- 相关测试和调用点

## 分步检查

1. 列出重复块各自的位置和差异点
2. 判断它们是真重复，还是只是长得像
3. 找出共同规则和少量差异参数
4. 设计最小公共抽象，别一次抽成万能黑盒
5. 抽取后回收旧实现，避免两套代码并存
6. 跑调用点相关验证，确认行为不变

## 修复要求

- 优先抽业务上真的共用的部分
- 参数和命名要能让调用点继续好读
- 删除旧重复实现，不要留下“新老两套都能跑”

## 完成标志

- 至少删掉一批真实重复块
- 新公共实现没有把调用点变得更绕
- 相关测试能证明语义没漂移

## 不要做

- 不要把两段只是表面像的代码硬合并
- 不要抽出一个什么都能干、最后谁都不敢动的万能工具
- 不要只新增公共方法，却保留原重复实现
