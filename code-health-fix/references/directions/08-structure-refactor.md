# 8. 代码结构重构

## 这个方向要解决什么

找“文件太胖、职责太乱、改哪里都牵一身”的结构问题。
结构重构像把一个塞满杂物的大抽屉分格，不是为了好看，是为了下次找东西不再全翻一遍。

## 什么时候把它列为不同评级

- `必须`：用户明确要求拆文件、拆大类、拆屎山，或当前文件已经严重阻碍修 bug
- `建议`：存在巨型文件、巨型类、超长函数、职责混杂，但还能勉强维护
- `可选`：结构一般，但主问题不在这里
- `不必`：当前范围只是小修小补，结构没有明显痛点

## 检查边界

- 一次只锁定 1 个目标文件、类，或 1 个强相关结构簇
- 结构重构不是“继续往原文件塞 helper”
- 做结构时如果同时看到了 bug、错误处理或测试缺口，要按真实证据把它们写进建议表和计划，不要靠“顺手补护栏”带过
- 不要因为做了这些配套动作，就跳过对应方向的评级和计划映射

## 先收集这些证据

- 目标文件行数、类职责、主要 public 方法
- 重复块位置、层次穿透点、依赖关系
- 相关测试和调用方
- 原文件里注释旧代码、历史兜底、兼容分支

## 分步检查

1. 记录改动前基线：体量、职责数、重复块位置
2. 划分哪些职责应该迁出，哪些必须留在原位
3. 设计新边界，保证命名和依赖方向更清楚
4. 搬职责时同步删旧实现，不要留下双份逻辑
5. 检查调用点是否仍然清晰，别把复杂度转移成更多绕路
6. 对照测试，确认重构前后行为没变

## 修复要求

- 优先迁职责，不要只抽几个静态工具函数装样子
- 新文件名、类名要能直接说出职责
- 如果原文件暂时净增长，必须明确标成“过渡态”
- 结构拆分后要同步删旧桥接和重复逻辑，至少删掉一批真正障碍物

## 完成标志

- 目标文件或类的体量、职责数、重复块至少有一项下降
- 新增文件职责清楚，旧实现没有继续保留双份
- 行为通过最小相关验证

## 不要做

- 不要把“新增 helper 但旧逻辑没删”说成拆文件
- 不要一下子扩到多个无关大文件
- 不要为了结构漂亮，顺手改公共协议和全仓命名
