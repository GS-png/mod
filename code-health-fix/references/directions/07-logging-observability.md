# 7. 日志与可观测性

## 这个方向要解决什么

找“问题出了以后，别人能不能顺着线索找到现场”的问题。
日志像监控摄像头，角度不对或者没开机，事故发生后就只能靠猜。

## 什么时候把它列为不同评级

- `必须`：关键路径出错难复现、异步任务多、外部调用多，或者已经看到日志缺失
- `建议`：模块有日志，但上下文不足、错误信息太空
- `可选`：低频内部工具，失败时本地调试成本很低
- `不必`：纯文档、纯样式、不会运行的资源

## 检查边界

- 重点看关键状态切换、失败路径、外部调用入口
- 不把“全仓统一日志框架改造”默认纳入本轮
- 同时兼顾可观测性和敏感信息保护

## 先收集这些证据

- 关键入口、状态切换点、异常处理分支
- 外部 API、数据库、文件、消息队列调用
- 现有日志格式、字段、关联 ID
- 线上或本地问题复盘线索

## 分步检查

1. 看关键路径是否有开始、失败、结束日志
2. 看错误日志有没有上下文，如请求 ID、对象 ID、状态值
3. 看异常是否保留堆栈和原始消息
4. 看异步流程能不能串起前后步骤
5. 看日志里有没有密码、token、完整路径等敏感信息
6. 看日志级别是否合理，避免全都打成错误

## 修复要求

- 只补关键点，不要海量加噪音日志
- 优先补能帮助定位根因的上下文
- 敏感数据要打码、截断或去掉

## 完成标志

- 别人可以靠日志复盘主要失败路径
- 关键错误日志保留足够上下文
- 修后日志不会把敏感信息直接抛出去

## 不要做

- 不要把每一行都加日志，结果噪音淹没信号
- 不要只有“执行失败”这种空话，没有对象和场景
- 不要为了可观测性牺牲安全性
