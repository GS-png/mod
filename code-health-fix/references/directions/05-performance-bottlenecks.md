# 5. 性能瓶颈

## 这个方向要解决什么

找“代码能跑，但跑得很笨”的地方。
性能问题像搬家时反复来回搬同一箱东西，不一定会崩，但会又慢又累。

## 什么时候把它列为不同评级

- `必须`：这是高频路径、渲染循环、批处理、热循环，或已经看到重复 IO、重复查询、明显阻塞
- `建议`：模块可能会被频繁调用，但缺少性能证据
- `可选`：低频后台任务、一次性工具脚本
- `不必`：纯文档、纯配置说明、不会运行的资源文件

## 检查边界

- 先盯高频路径和大头开销，不做“全仓性能普查”
- 没有证据时别瞎猜微优化
- 如果修法会明显增加复杂度，先算收益再决定

## 先收集这些证据

- 热点入口、循环、批处理、渲染更新点
- IO、数据库、网络、磁盘访问
- 大集合操作、排序、分组、序列化
- 现有 benchmark、profiling、日志、计数器

## 分步检查

1. 确认这段代码多久跑一次，输入规模有多大
2. 找重复 IO、重复查询、重复计算、重复分配
3. 看循环里是否做了昂贵操作
4. 看缓存是否无上限、命中差、失效策略混乱
5. 看同步阻塞是否卡在高频路径
6. 看有没有可以用一次计算、多处复用的机会

## 修复要求

- 优先减少次数，再考虑减少单次成本
- 用最容易解释的修法，不要把简单逻辑换成花哨黑魔法
- 修后尽量给出次数、耗时、分配量或 IO 次数下降的证据

## 完成标志

- 能说清瓶颈点在哪，为什么它是大头
- 修后有具体收益证据，哪怕只是调用次数减少
- 没把代码复杂度抬得过高

## 不要做

- 不要为了“可能更快”去改一堆低频代码
- 不要拿格式化、命名调整冒充性能优化
- 不要只说“理论上更快”，却没有任何证据入口
