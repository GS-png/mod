# 1. Bug 与逻辑问题

## 这个方向要解决什么

找“程序做错事”的地方。
重点不是代码好不好看，而是输入进去以后，结果有没有算错、判错、漏判或状态走偏。

## 什么时候把它列为不同评级

- `必须`：用户明确说“有 bug”“有回归”“逻辑不对”，或者当前模块是核心流程、分支密、状态切换多
- `建议`：这是业务规则模块、数据转换模块、状态协调模块，逻辑复杂但暂时没看到明确事故
- `可选`：只是简单 DTO、薄封装、纯转发层，逻辑很薄
- `不必`：纯文档、纯静态资源、纯样式文件，没有运行时逻辑

## 检查边界

- 只查逻辑正确性，不把结构重构和格式化混进来
- 至少补看直接调用点、相关测试、相关配置或协议
- 如果项目有 `api/`、SDK、DLL 文档，先把字段名和返回语义查准

## 先收集这些证据

- 入口函数、控制器、服务层主流程
- 分支密集函数、状态切换函数、数据映射函数
- 最近改动附近的测试
- 需求文档、注释、协议定义、默认值配置

## 分步检查

1. 写清输入、输出、副作用
2. 拆出正常路径、失败路径、边界路径
3. 逐个确认空值、默认值、空集合、零值、负值、最大最小值
4. 看条件分支有没有漏分支、反条件、顺序错误、提前返回误伤
5. 看状态变化前后是否一致，失败时是否需要回滚
6. 看时间、时区、排序、分页、下标、计数有没有“差一位”问题
7. 对照测试，确认旧 bug 是否能被回归用例卡住

## 修复要求

- 优先选最小安全修法，不要顺手重写整段逻辑
- 改逻辑时同步补回归测试，至少覆盖一个真实失败路径
- 如果改动会影响外部协议，要先确认边界，不要偷偷改公共行为

## 完成标志

- 至少确认 1 条正常路径、1 条失败路径、1 条边界路径
- 关键分支有代码证据，不靠猜
- 如果落了修复，旧问题在新增测试下会失败，修后会通过

## 不要做

- 不要把“感觉可读性一般”当成逻辑 bug
- 不要为了顺手统一风格，扩大到无关文件
- 不要只看 happy path 就宣布“逻辑没问题”
