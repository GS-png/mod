# 3. 错误处理与异常管理

## 这个方向要解决什么

找“出错以后系统怎么摔、摔得别人能不能看懂”的问题。
程序出错不可怕，可怕的是出了错以后像断电一样，没人知道发生了什么。

## 什么时候把它列为不同评级

- `必须`：有 IO、网络、数据库、外部进程、文件系统、重试逻辑，或者已经看到空 `catch`、吞错
- `建议`：模块会失败，但失败后果相对可控
- `可选`：纯计算逻辑、不会抛太多异常的薄封装
- `不必`：静态资源、说明文档、纯样式

## 检查边界

- 重点查失败路径，不只看成功路径
- 同时看调用方怎么接收错误，别只盯抛错点
- 如果系统有统一错误模型，先查现有约定，不要自己发明一套

## 先收集这些证据

- `try/catch/finally`、错误码、Result 模型
- IO、网络、数据库、进程调用代码
- 重试、超时、取消、回滚逻辑
- 相关日志和测试

## 分步检查

1. 列出当前流程可能失败的节点
2. 看每个失败点是抛异常、返回错误码，还是直接吞掉
3. 看调用方收到错误后能不能区分原因和做出正确处理
4. 看部分成功后失败的场景，状态会不会半更新
5. 看重试是否会重复提交、重复写入、重复副作用
6. 看异常信息是否保留上下文，而不是只剩一句“失败了”

## 修复要求

- 保留原始异常链和必要上下文
- 明确失败后的状态收口方式，比如回滚、清理、提示调用方
- 重试逻辑要避免重复副作用
- 至少补一个异常路径测试或最小复现

## 完成标志

- 关键失败路径都能被看见
- 调用方能收到可处理的结果，不用靠猜
- 修复后失败场景不会把状态留在半成品状态

## 不要做

- 不要用空 `catch` 或统一 `catch (Exception)` 直接吞掉问题
- 不要把所有错误都改成同一句提示
- 不要只修抛错点，不看调用方是否还能正确处理
