# 2. 安全隐患

## 这个方向要解决什么

找“外部输入能不能把系统带偏、打穿、泄露数据”的地方。
安全问题像门锁，平时看不见，一旦有缝，别人会直接从缝里钻进来。

## 什么时候把它列为不同评级

- `必须`：有外部输入、权限判断、文件路径、命令执行、反序列化、密钥处理、敏感数据
- `建议`：模块会接触用户输入、配置输入、网络响应，但暂时没直接看到高危点
- `可选`：内部纯计算模块，几乎不接触外部输入
- `不必`：纯静态资源、纯排版文档、不会参与运行时输入处理

## 检查边界

- 重点看输入入口、权限入口、敏感数据流转
- 不把“升级依赖”“全仓安全审计”默认拉进来，除非用户明确要做
- 如果修复需要改变公共权限模型，先把当前边界内能单独落地的部分做好

## 先收集这些证据

- 接口层、命令入口、文件读写入口、配置读取入口
- 权限校验、中间层、网关、过滤器
- 日志输出、异常信息、调试打印
- 涉及 token、密码、路径、脚本、SQL、序列化的代码

## 分步检查

1. 标出所有外部输入从哪里进来
2. 看输入有没有校验、清洗、长度和格式限制
3. 看权限判断是不是在正确位置发生，是否可能绕过
4. 看敏感数据有没有被日志、异常、返回值直接带出去
5. 看路径拼接、命令拼接、查询拼接是否可注入
6. 看反序列化、动态加载、脚本执行是否限制来源和类型
7. 看失败路径会不会暴露内部实现细节

## 修复要求

- 优先在入口处收口，而不是在后面层层补丁
- 敏感数据默认打码或不输出
- 权限校验要放在真正能拦住请求的位置
- 修复后至少补一个“恶意输入或越权输入”用例

## 完成标志

- 能说清风险入口、利用方式和堵口方式
- 高危输入路径都有明确保护
- 修复后日志、异常、返回值不再泄露敏感信息

## 不要做

- 不要把“感觉可能不安全”当结论，必须有入口和影响
- 不要为了追求全面，没证据就给全仓贴安全问题标签
- 不要把依赖升级当成默认修法
