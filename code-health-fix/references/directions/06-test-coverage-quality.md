# 6. 测试覆盖与质量

## 这个方向要解决什么

找“代码改了以后谁来拦车”的问题。
测试像护栏，不是为了好看，是为了下次有人再改时别直接冲出山路。

## 什么时候把它列为不同评级

- `必须`：本轮要改逻辑、异常路径、结构、并发或安全问题
- `建议`：模块已有测试但明显只测 happy path
- `可选`：当前是纯文档或极小改动，且已有强验证手段
- `不必`：完全不涉及运行时代码，只改静态文案

## 检查边界

- 重点查“能不能卡住这轮要改的问题”
- 不追求一次把整个模块测试补满
- 如果仓库测试设施很弱，至少给最小复现或编译级保护

## 先收集这些证据

- 相关测试目录、命名规则、测试基类
- 最近改动附近的测试
- 历史 bug 对应测试
- 能跑的最小测试命令

## 分步检查

1. 看当前变更点有没有现成测试覆盖
2. 看测试是不是只测成功路径
3. 看边界值、异常路径、空值、配置差异有没有测试
4. 看断言是否过弱，只断“没有报错”
5. 看旧 bug 有没有回归用例，防止以后再犯
6. 看测试数据是否太假，导致测不出真实问题

## 修复要求

- 新增测试要能在旧问题存在时失败
- 结构重构时优先守住行为，不用顺手大改测试风格
- 跑最小相关测试，写清没跑的范围和原因

## 完成标志

- 关键修复点至少有一个能卡住旧问题的用例
- 测试命名和断言能让人看懂在保护什么
- 即使没法补齐全量测试，也说明了当前保护边界

## 不要做

- 不要只补 happy path 测试凑数量
- 不要新增一堆与本轮改动无关的测试表演工作
- 不要跑不通也不说明，直接写“已验证”
