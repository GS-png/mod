# Engineering：性能、资源与并发

## 1. 目的

控制运行成本、延迟、内存、IO、并发、异步处理、资源释放、缓存和高频路径风险。

## 2. 何时加载

触达以下任一情况时加载：

- 高频请求路径。
- 无界或大数据循环。
- 大对象、文件、stream、upload、download、export。
- 数据库查询、外部网络调用、cache、queue、lock、subscription、timer、worker、scheduler。
- shared mutable state、async tasks、retry、backoff、cancellation、timeout、rate limiting。
- 声称性能提升或并发安全。

# 性能资源并发

## 任务本质
以明确性能目标为约束，控制资源占用、并发度和过载行为。
目标不是局部跑得更快，而是在目标负载下保持可接受的延迟、吞吐、资源效率和稳定性，并在过载时优雅退化而不是级联失效。
性能目标、资源边界或并发策略不清的实现，一律视为高风险实现。

## 必读规范
- 先定义性能目标；延迟、吞吐、并发、容量和成本边界不清，不开始改动。
- 先找瓶颈，再做优化；不要用猜测代替测量，不要先上并发再找原因。
- 资源必须有预算；CPU、内存、连接、线程、协程、队列、缓存和 I/O 不能无限增长。
- 并发必须有上限；不要把无界并发、无界队列或无限重试当成扩展性。
- 超时必须显式；重试必须有限，并带退避与抖动。
- 依赖必须隔离；慢依赖、热点依赖和高成本依赖不能拖垮不相关功能。
- 过载必须可控；限流、准入控制、背压、丢弃、降级或 load shedding 要明确。
- 队列必须可治理；生产速率、消费速率、积压上限、过期策略和优先级要清楚。
- 多租户或多业务共享资源时，必须控制 noisy neighbor；公平性、配额和隔离策略要明确。
- 缓存、批处理、异步化和并行化只能在正确性、顺序性和资源收益明确时使用。
- 性能设计必须同时说明对延迟尾部、吞吐、资源效率、成本和稳定性的影响。
- 关键路径必须可观测；延迟分布、饱和度、错误率、积压和丢弃量要能看到。
- 新增或修改性能、资源、并发策略，必须写清目标负载、瓶颈假设、保护措施和失效后果。

## 完成标准
- 能明确说清性能目标、目标负载和资源预算。
- 能明确说清瓶颈在哪里，并发上限在哪里，过载时怎么处理。
- 能明确说清哪些路径同步、哪些异步、哪些可降级、哪些必须保真。
- 高负载下不会因无限排队、无限重试、热点竞争或慢依赖导致级联失效。
- 关键指标可观测，优化或退化效果可验证。
- 性能与资源设计能对应明确业务目标，而不是只写“做了优化”。

## 反例信号
- 没有性能目标，直接做“优化”。
- 用无界线程、无界协程、无界连接池或无界队列顶并发。
- 依赖变慢时持续堆请求、堆重试、堆积压，最终拖垮全链路。
- 只看平均延迟，不看尾延迟、饱和度、积压和丢弃。
- 为了吞吐盲目并行、批处理或缓存，但顺序性、资源占用和收益说不清。
- 多租户共享资源时没有限流、配额或隔离，任由 noisy neighbor 影响全局。
