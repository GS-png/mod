# Engineering：文档、注释与可观测性

## 1. 目的

保证文档描述真实行为，注释解释必要约束，日志 / 指标 / trace / 告警帮助排障且不泄露敏感信息。

## 2. 何时加载

触达以下任一情况时加载：

- README、AGENTS.md、docs、examples、API docs、migration notes、changelogs、comments、runbooks。
- logs、error messages、metrics、alerts、traces、audit records、monitoring config。
- public interfaces、configuration、environment variables、setup steps、deployment steps、troubleshooting behavior。

# 文档可观测性

## 任务本质
让文档能持续反映系统当前状态、关键决策、责任归属、变更轨迹和运行证据。
目标不是“把文档写出来”，而是让人能快速判断文档是否可信、是否过期、该看哪一份、该找谁、该用什么证据验证。
不可追踪、不可验证、不可判断新旧的文档，一律视为高风险文档。

## 必读规范
- 先定义文档对象、受众、用途和 owner；对象不清，不开始写。
- 文档必须可追踪；来源、版本、变更记录和关联代码/配置/决策要能找到。
- 关键决策必须留痕；背景、决定、理由、影响和后续替代关系要清楚。
- 文档必须分型清楚；教程、操作指引、参考说明、原理解释不要混写。
- 文档必须标明适用范围、前提条件、环境差异和失效边界；不要把局部经验写成通用事实。
- 文档必须能映射到当前系统；接口、配置、依赖、运行方式和观测入口要可验证。
- 运行类文档必须给出验证入口；日志、指标、追踪、仪表盘、告警、运行命令或检查点要明确。
- 文档必须可维护；和代码一样纳入版本控制、评审、变更流程和必要的自动检查。
- 文档必须能判断新旧；更新时间、适用版本、当前状态和是否已废弃要明确。
- 新增或修改文档，必须写清 owner、适用对象、证据来源和未覆盖边界。

## 完成标准
- 能明确说清这份文档给谁看、解决什么问题、由谁负责。
- 能明确说清文档对应哪个系统版本、哪类环境、哪组决策和哪条运行路径。
- 能明确说清文档中的关键结论由什么证据支持，去哪验证。
- 文档变化可追踪，旧结论是否失效可判断，替代关系可定位。
- 读者能在最短路径内找到正确文档，而不是在说明、原理、操作和参考之间来回猜。

## 反例信号
- 文档没有 owner、没有版本、没有更新时间，没人知道还能不能信。
- 决策写了结论，没写背景、理由和影响，后人无法判断是否仍适用。
- 教程、操作步骤、参考参数、原理解释混成一篇，读者无法快速定位。
- 文档描述和当前代码、接口、配置、环境不一致，却没有失效标记。
- 运行文档只有口头经验，没有日志、指标、追踪、命令或检查点。
- 文档很多，但没人知道哪份是当前真相，哪份已经废弃。
