# Engineering：隐私与权限

## 1. 目的

防止不安全输入处理、权限绕过、密钥泄露、隐私违规、注入漏洞、SSRF、多租户越权和不安全文件 / 网络行为。

## 2. 何时加载

触达以下任一情况时加载：

- Authentication、authorization、identity、roles、scopes、sessions、tokens。
- Personal data 或 sensitive business data。
- External input、file upload/download、paths、URLs、templates。
- SQL、command execution、shell、queries、expressions。
- Network calls、webhooks、external integrations。
- Logs、metrics、traces、errors、audit events。
- Crypto、signing、hashing、serialization、parsing。
- CORS、CSRF、cookies、OAuth、redirect、tenant / org / workspace 边界。

# 隐私与权限

## 任务本质
只允许被授权的主体，在被允许的条件下，访问被允许的资源。
只收集、使用、暴露和保留业务必需的个人信息。
权限边界或隐私边界不清的实现，一律视为高风险实现。

## 必读规范
- 先识别主体、资源、动作、数据类别和可见范围；对象不清，不开始改动。
- 认证和授权分开；先确认你是谁，再判断你能做什么。
- 权限必须默认拒绝，按最小权限授予；访问决策必须按请求、按资源执行。
- 授权必须在服务端强制执行；不能只依赖前端隐藏、路由控制或客户端字段。
- 每个对象访问都要校验主体、动作、资源和上下文；不要把“知道 ID”当成有权限。
- 角色、策略、继承、例外和作用域必须显式；不要靠散落判断或隐式约定。
- 个人信息必须最小化处理；收集目的、字段范围、可见范围、保留期限和删除方式要明确。
- 默认不暴露敏感字段；非必需不返回，非必需不记录，非必需不复制。
- 权限变化、敏感访问、导出、分享、删除等关键操作必须可审计、可追踪。
- 跨服务传递身份、角色、租户、组织或资源范围时，语义必须一致；不要在链路中丢失授权上下文。
- 新增或修改隐私与权限规则，必须写清保护对象、授权规则、例外条件、影响面和收口方式。

## 完成标准
- 能明确说清谁能对什么资源执行什么动作。
- 能明确说清哪些数据属于个人信息，为什么收集，谁可见，保留多久，如何删除。
- 每个受保护对象都能在服务端正确拒绝未授权访问。
- 权限失败、越权尝试、敏感访问和高风险操作都可审计、可追踪。
- 权限与隐私设计能对应明确业务规则和风险，而不是只停留在“加个登录”或“隐藏按钮”。

## 反例信号
- 登录了就默认有权限，认证被当成授权。
- 只在前端做权限控制，服务端不做对象级校验。
- 用户可以通过改 ID、改参数、改路径访问不属于自己的资源。
- 收集了不必要的个人信息，或用途、可见范围、保留删除规则说不清。
- 敏感字段被默认返回、默认导出、默认写日志。
- 跨服务后身份还在，但资源范围、租户范围或角色语义丢了。
