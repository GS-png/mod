# Engineering：正确性、失败处理与幂等

## 1. 目的

保护运行行为、业务逻辑、状态一致性、失败暴露、重试恢复和重复执行安全。

## 2. 何时加载

触达以下任一情况时加载：

- Bug 修复、既有增强、实现替换、行为变更、新能力、架构迁移。
- IO、持久化、状态、业务逻辑、后台任务、重试、错误处理、用户可见结果。
- async job、queue、scheduler、worker、event handler、webhook、external integration。
- 任何可能在运行时失败的改动。

# 正确性与失败处理

## 任务本质
先定义什么叫正确，再定义失败时怎么处理。
目标不是“尽量不报错”，而是保证结果正确、状态正确、副作用可控，且失败不会被放大成级联故障。
正确性不清或失败路径未定义的实现，一律视为高风险实现。

## 必读规范
- 先定义正确性：业务不变量、数据约束、接口契约、状态转换和副作用边界要清楚。
- 成功条件和失败条件都要显式；不要只设计 happy path。
- 必须区分失败类型：瞬时失败、永久失败、超时、过载、部分成功、重复提交、顺序错乱、依赖不可用。
- 超时必须显式；不能无限等待。
- 重试只用于可恢复的瞬时失败；必须限制次数，并使用退避与抖动。
- 有副作用的操作必须保证幂等，不能把重试变成重复执行。
- 长流程或跨服务操作必须定义补偿、回滚或人工收口方式；不要把中间失败留成脏状态。
- 依赖长期异常时必须快速失败、熔断、隔离或降级；不要持续放大故障。
- 接口必须明确成功、失败、部分成功和未知状态的语义；错误码、返回值和日志语义要一致。
- 数据写入、消息投递、任务执行要明确去重、顺序、一致性和 source of truth。
- 关键共享状态必须明确一致性策略；不要默认“最终会对”。
- 失败必须可观测：日志、指标、追踪、告警和重试结果要能区分。
- 失败处理要说明对正确性、可用性、性能、成本和恢复时间的影响。
- 新增或修改失败处理策略，必须写清触发条件、保护范围、退出条件和副作用。

## 完成标准
- 能明确说清什么结果算正确，什么状态算失败。
- 能明确说清每类失败怎么处理、不处理什么、何时停止重试。
- 能明确说清哪些操作幂等，哪些副作用不可重放。
- 能明确说清部分成功、超时和未知状态怎么收口。
- 能通过测试或演练证明关键不变量、错误路径和恢复路径成立。
- 失败不会无控制地扩散成级联故障。

## 反例信号
- 只有成功路径，没有失败路径定义。
- 遇错就重试，但没有幂等、上限、退避或抖动。
- 超时、取消、部分成功、未知状态没有明确语义。
- 一个操作失败后留下脏数据、重复副作用或不可恢复中间状态。
- 对外宣称成功，但数据、消息或副作用并未真正完成。
- 依赖异常时持续重试、持续阻塞或持续级联放大故障。
