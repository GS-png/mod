# Engineering：正确性、失败处理与幂等

## 1. 目的

保护运行行为、业务逻辑、状态一致性、失败暴露、重试恢复和重复执行安全。

## 2. 何时加载

触达以下任一情况时加载：

- Bug 修复、既有增强、实现替换、行为变更、新能力、架构迁移。
- IO、持久化、状态、业务逻辑、后台任务、重试、错误处理、用户可见结果。
- async job、queue、scheduler、worker、event handler、webhook、external integration。
- 任何可能在运行时失败的改动。

## 3. 必查项

实现前识别：

- 问题根因、触发条件、影响范围和最小修复点。
- 正常路径。
- 空值、缺失、非法、畸形、越界、重复、过期、未授权输入。
- 部分成功状态。
- 重试、重复执行、重入、取消、超时、回滚行为。
- 调用方预期和下游副作用。
- 现有错误类型、错误码、日志模式和恢复路径。

## 4. 正确性规则

- 不把未知状态当成功。
- 不添加 fake success、placeholder branch、dummy return 或只让流程“看起来完整”的代码。
- 不留下 TODO、空分支、不可达 fallback、静默 no-op，除非任务明确要求并记录原因。
- 修改内部实现时不得意外改变外部行为。
- 除非任务明确是行为变更，否则保持既有契约。
- 新增 TODO 只能用于非必需后续改进；不得用 TODO 代替本次必须完成的行为。
- 优先修复根因，不用一层补丁覆盖另一层补丁。
- 如果必须增加临时保护、兼容层或 fallback，必须说明根因、触发条件、权威路径、移除条件和验证方式，避免临时方案永久化。

## 5. 失败处理规则

- 失败必须显式、可观察、可定位。
- 不吞异常。
- 捕获最小有用错误范围。
- 错误信息包含定位上下文：阶段、输入身份、依赖、操作或状态摘要。
- 失败后系统不得留下不一致状态。
- 必要时使用 transaction、rollback、compensation、controlled retry 或 explicit failure result。
- 恢复行为必须确定且可测试。

## 6. 幂等与防重复

- 操作可能执行多次时，必须设计幂等或防重复保护。
- 重复请求、重复 job、重试、webhook redelivery、页面刷新、CLI 重跑不得产生非预期重复状态。
- exact idempotency 不可能时，必须说明剩余风险并限制影响范围。
- migration、batch、backfill 应支持安全重跑；不能重跑时必须写清原因和保护措施。

## 7. 状态一致性

- 不更新多个状态源而没有单一 authority、transaction 或 compensation strategy。
- 不引入 shadow state、隐藏 cache 或重复 truth source。
- 多系统写入必须定义顺序、失败恢复和 reconcile 行为。
- 可能存在 stale state 时，必须定义检测和解决方式。

## 8. 确定性与边界场景

涉及以下内容时必须说明确定性策略：

- 时间、时区、日期边界。
- 排序、分页、游标、去重。
- 随机数、采样、重试 jitter。
- 浮点、金额、舍入、精度。
- locale、编码、大小写、Unicode。
- 并发顺序、文件系统顺序、网络返回顺序。
- map / object 未排序遍历。

不得引入依赖当前机器时间、文件系统顺序、未排序遍历或网络返回顺序的隐式行为，除非项目已有约定并说明原因。

## 9. 验证

相关验证应覆盖：

- 正常路径。
- 边界路径。
- 非法输入路径。
- 依赖失败路径。
- 部分成功 / 回滚路径。
- 重复执行 / 重试 / 重复输入路径。
- 权限或信任边界路径。

无法完全验证时，交付必须说明未验证项、原因和风险。

## 10. 交付补充

```text
失败模式：<考虑过哪些失败>
幂等 / 防重复：<策略或风险>
恢复 / 回滚：<失败后如何恢复>
确定性：<时间/排序/分页/随机/并发等是否涉及>
未验证边界：<未覆盖项>
```
