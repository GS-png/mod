# 日志与可观测性

## 任务本质

- 让关键路径可观察、可关联、可定位。
- 日志不是凑输出；日志是定位问题、追踪状态、还原事实和支撑审计的证据。
- 日志要服务运行，不要制造噪音。
- 该有的地方必须有；不该记的不要记；记了就要能查、能串、能解释。

## 必读规范
- 关键路径必须可观测；入口、出口、状态变化、外部调用、异常和关键结果不得缺日志。
- 日志默认结构化；事件名、级别、对象标识和上下文字段必须稳定。
- 有链路上下文时，必须带 request id、trace id、task id 或同类关联标识。
- 只记关键节点，不记流水账；日志必须能帮助定位问题。
- 严禁输出密码、token、密钥、完整凭证和敏感数据；输出前必须脱敏、清洗、防注入。
- 安全相关动作必须留审计痕迹；拒绝、鉴权失败、权限变化和关键数据操作不得静默。
- 日志不是指标替代品；需要告警、趋势或 SLO 判断时，必须补指标。
- 提示和规则写法必须短、结果导向；不要把日志要求写成 process-heavy 提示栈。

## 完成标准
- 关键路径有日志，失败路径也有日志。
- 同一请求或任务可以靠关联标识串起来。
- 日志字段稳定，可检索、可聚合、可过滤。
- 成功、失败、重试、回滚、拒绝能区分。
- 敏感数据未泄露，脱敏规则有效。
- 交付前已验证关键日志真实可见、字段正确、级别合理。

## 反例信号
- 没报错时几乎没日志，报错后也还原不了现场。
- 只有大段文本，没有稳定字段，没有关联 id。
- 每层都在刷日志，真正关键事件反而淹没。
- 把密码、token、密钥、身份证号、手机号或原始请求直接打进日志。
- 用日志硬扛告警、统计和 SLO，缺少指标。
- 为了“看起来完整”写成长流程要求，导致规则冗长、噪音大、命中差。
