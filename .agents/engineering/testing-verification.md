# Engineering：测试与验证

## 1. 目的

确保变更由相关证据证明，而不是仅靠代码阅读、类型推断或假设。

# 测试验证

## 任务本质
用客观证据证明改动正确、约束成立、回归未被破坏。
目标不是“把测试跑了”，而是证明需求满足、关键风险被覆盖、失败能被及时发现。
没有验证目标、没有有效证据或只有口头说明的改动，一律视为高风险改动。

## 必读规范
- 先定义要验证什么；需求、约束、边界条件、失败路径和回归风险不清，不开始改动。
- 测试要按风险和反馈速度分层；优先用更小、更快、更聚焦的测试验证能在小范围证明的问题。
- 端到端测试只覆盖跨系统主链路和关键集成风险；不要用大测试替代本可由小测试证明的问题。
- 测试必须可判定；输入、触发条件、预期结果和失败判定要明确。
- 测试必须覆盖正常路径、边界条件、异常路径和回归风险；不要只测 happy path。
- 测试必须尽量稳定、可重复、少依赖共享外部环境；能 hermetic 就不要依赖不受控外部系统。
- Mock、stub、fake 只能用于隔离依赖和提高聚焦度；不要因为过度替身而失去关键真实约束。
- 验证不只看功能结果；涉及正确性、性能、权限、数据、兼容性或迁移的改动，必须验证对应影响面。
- 覆盖率只能做辅助信号，不能代替测试质量和风险覆盖。
- 发现 flaky test 必须收口；不能长期依赖重跑掩盖不稳定。
- 新增或修改测试策略，必须写清验证目标、证据类型、覆盖范围和未覆盖风险。

## 完成标准
- 能明确说清这次改动验证了什么，没有验证什么。
- 能明确说清每个关键风险由哪类测试或哪条证据覆盖。
- 关键路径、边界条件、异常路径和已知回归点都有对应验证。
- 测试结果可重复、可判定，失败时能定位到具体问题范围。
- 大测试数量受控，测试组合整体可维护、可运行、可持续。
- 结论基于证据，而不是基于“理论上应该没问题”。

## 反例信号
- 只说“已自测”或“已跑通”，但没有明确验证目标和证据。
- 只有 happy path，没有边界条件、异常路径和回归验证。
- 用大量端到端测试覆盖本应由小测试解决的问题。
- 测试依赖共享环境、随机时序或外部状态，结果不稳定却长期不处理。
- 只看覆盖率数字，不看关键路径、关键约束和失败路径是否真的被验证。
- 测试很多，但失败时不能定位问题范围，或通过重跑来掩盖 flaky。
