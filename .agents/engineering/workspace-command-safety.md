# Engineering：工作区与命令安全

## 1. 目的

保护用户工作、仓库状态、生成产物和外部系统，避免误删、误覆盖、误发布、误部署和破坏性命令。

## 2. 工作区规则

修改文件前：

- 工具允许时检查当前 working tree status。
- 识别已有用户改动。
- 不覆盖、revert、format、移动或删除用户改动，除非用户明确要求。
- 不假设 uncommitted changes 都是当前 agent 产生的。
- 避免触碰无关文件的 broad formatting。

# 工作区命令安全

## 任务本质
安全地执行工作区内命令，限制作用范围、权限和破坏面。
目标不是“命令能跑通”，而是命令可预期、可约束、可审计、失败不扩大损害。
命令来源、参数边界、执行范围或权限边界不清的改动，一律视为高风险改动。

## 必读规范
- 先判断是否必须执行命令；能用语言内建 API、库函数或工具接口完成的，不直接调用 shell。
- 所有外部输入一律视为不可信；用户输入、文件内容、检索结果、环境变量和路径字符串都不能直接拼进命令。
- 命令与参数必须分离构造；不要把整条命令当字符串拼接执行。
- Shell 场景必须显式引用变量并安全传参；不要依赖隐式分词、通配展开或命令替换。
- 每条命令都要显式限定工作目录、目标路径和作用对象；禁止默认作用于未知当前目录或宽泛路径。
- 默认非破坏；删除、覆盖、移动、批量替换、权限修改等高风险命令必须先缩小范围，再执行。
- 高风险命令必须可预览、可回退或可恢复；不能直接对不可重建内容做一次性破坏操作。
- 执行身份必须最小权限；不要默认使用高权限账户、sudo 或跨工作区能力。
- 环境与 PATH 必须可控；不要依赖本机隐式安装、别名、shell profile 或不透明包装命令。
- 命令失败必须显式处理；失败不能静默吞掉，也不能在未知状态下继续连锁执行。
- 命令执行必须可审计；执行了什么、在哪个目录、针对哪些对象、结果如何，要能追踪。
- 新增或修改命令执行逻辑，必须写清触发来源、参数边界、作用范围、权限要求和失败收口方式。

## 完成标准
- 能明确说清为什么必须执行该命令，为什么不能用更安全的替代方式。
- 能明确说清命令的输入来源、参数边界、工作目录和作用对象。
- 能明确说清命令在最小权限下执行，且不会越出预期工作区和目标范围。
- 高风险命令有预览、保护、审计和失败收口措施。
- 外部输入不能直接变成可执行命令片段。
- 命令执行结果可验证，失败后系统和工作区不会进入不可控状态。

## 反例信号
- 把用户输入、文件内容或路径直接拼进 shell 字符串执行。
- 依赖当前目录、shell 别名、profile、全局环境或隐式 PATH 才能正确执行。
- 用宽泛路径、通配符或递归命令直接改写、删除或移动大量文件。
- 默认使用高权限执行命令，或命令实际作用范围超出当前工作区。
- 命令失败后继续执行后续步骤，且没有中止、告警或收口。
- 只能证明“命令跑过了”，但说不清它改了什么、在哪执行、为什么安全。
