# Engineering：边界划分
## 1. 目的

防止职责污染、大文件继续膨胀、跨层捷径、重复权威、循环依赖、公共 API 泄露和新功能堆进旧文件。

## 2. 何时加载

触达以下任一情况时加载：

- 新建、移动、拆分、合并文件或模块。
- 修改目录职责、模块边界、分层、调用方向或公共 API。
- 新增 feature、endpoint、page、job、command、integration、service、schema、permission、config 或 shared utility。
- 需要判断“改已有文件还是新建 owner”。

# 边界划分

## 任务本质
按业务语义、上下文、职责、依赖、数据、契约、部署和变更影响面划清边界。
目标不是把结构分得好看，而是降低耦合、限制变更扩散、支持独立演进、限制故障扩散。
边界不清的实现，一律视为高风险实现。

## 必读规范
- 先定系统边界，再定模块和服务边界；范围不清，不开始改动。
- 边界按业务语义、职责和变化原因划分；模块优先按职责与易变设计决策切，不按页面、流程、技术层、目录或临时实现反推。
- 模块必须隐藏易变实现，只暴露稳定接口；禁止跨模块依赖内部细节。
- 服务边界必须围绕单一业务能力或 bounded context；不要为拆而拆，不要切成过细服务。
- 每个服务必须明确 owner、职责、接口契约、数据归属和运行/部署归属。
- 数据必须有主；source of truth、可复制读、禁止直连写要明确。
- 接口是演进边界；改契约必须评估兼容性和调用方影响，不得把内部实现泄漏为外部约定。
- 分布式场景必须补齐部署映射；软件构件到环境、节点、容器和网络通道的映射要清楚。
- 跨进程、跨容器、跨网络、跨 API 的位置，都按信任边界处理。
- 边界要能被团队真正拥有；不要让多个团队长期共改同一职责，也不要让单个团队承担失控的认知负荷。
- 禁止跨服务共享写库、共享私有 schema、共享内部实现，或直连他方数据库类型。
- 跨边界通信必须显式；API、事件、命令和消息格式要清楚。
- 如果两个服务长期高频互调、接口过碎或改动总是联动，边界有问题，必须重画。
- 边界设计必须说明对性能、可用性、安全性、可维护性、可测试性和可部署性的影响。
- 新增、拆分、合并边界，必须写清收益、代价、替代方案和影响面。

## 完成标准
- 能明确说清系统内外、上下游和外部接口。
- 能明确说清每个边界负责什么、不负责什么。
- 能明确说清依赖方向、数据归属、通信方式和故障影响面。
- 单点需求改动不应无理由扩散到多个无关边界。
- 边界决策必须能对应业务目标或质量目标，不能只凭习惯。

## 反例信号
- 按页面、流程、技术层、目录或表结构硬切边界。
- 一个服务横跨多个 bounded context，或多个服务共享同一写库 / 私有 schema。
- 对外 API 直接暴露内部模型、表结构或实现细节。
- 服务长期高频互调、接口过碎、数据无主、改动总是联动。
- 图能画出来，但 owner、契约、数据归属、故障影响面说不清。
